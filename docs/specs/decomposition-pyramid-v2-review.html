Candidate C v2: assumption surfacing & verification

Your idea from today's granularity discussion, specced: every node states what it's silently assuming, the checkable assumptions get verified with targeted searches, and broken assumptions correct the forecast before it's made. Mark each unit, note anything, copy the markdown back to chat. No code until this comes back.

contextWhat v2 adds — and why it beats deeper trees

The design principle that came out of today's discussion, made concrete.

Decomposition earns its keep only while the children are more knowable than the parent — depth for its own sake just multiplies noise. v2 adds granularity on a different axis: every estimate silently rides on assumptions ("the referendum happens as scheduled", "the source measures what we think"). v2 makes them explicit and verifies the checkable ones. A verified assumption replaces a hidden guess with a fact — the one form of added granularity that reduces error instead of compounding it.

The P1 Bitcoin miss is the proof case: the forecast silently assumed the eligible window covered all history. That assumption was checkable and false. We fixed it with a prompt patch; v2 would catch that whole class structurally.

decisionThe Assumption model

What the decomposer must state for every node.

Each node carries 0–3 assumptions, each with:

  • text — falsifiable plain wording ("the referendum is officially scheduled before Sept 4").
  • load_bearing — would the estimate change materially if this were false?
  • verifiability — researchable (a search can settle it now) or unverifiable (about the future / unknowable).

Zero assumptions is a legitimate answer — the prompt forbids manufacturing filler. At runtime each assumption gains a status: verified ✓ falsified ✗ unverified ○, plus a one-line evidence citation.

Review prompts
  • Is 0–3 assumptions per node the right budget, or should the root allow more?

decisionThe verification pass

How checkable assumptions actually get checked.

After decomposition, before any leaf is estimated: collect all researchable assumptions across the tree (deduplicated), and for each run one targeted search + one cheap LLM verdict call ("does this evidence verify, falsify, or fail to settle it?"). Hard budget: max_assumption_verifications per question (default 6), inside the existing per-question search caps. Failures degrade to "unverified" with a trace note — never crash.

Worked example — Iceland referendum Node: "referendum held before Sept 4" · assumption: "the referendum is officially scheduled" (load-bearing, researchable) → search finds the government decree with a date → verified ✓ → the leaf estimates from a fact, not a guess about scheduling.
Review prompts

decisionVerified-false handling — the jackpot case

What happens when an assumption turns out to be wrong.

A falsified assumption is injected prominently into the owning node's estimation prompt: "NOTE: the assumption you might make — X — is FALSE: <evidence>." The node then reasons from corrected facts. This is context injection, not arithmetic — no automatic probability adjustment, because the right response to a broken assumption depends on what broke.

Counterfactual: in the Bitcoin case, verification of "the window covers all of history" would have returned FALSE (question opened May 2026), and the leaf would have reasoned about a rally from the current price — which is exactly what it did after our manual fix (0.99 → 0.06).

riskdecisionCoupling: confidence caps + fragility pull — the key call

How UNVERIFIED assumptions affect the output. The most consequential unit on this page.

Assumptions deliberately do not multiply into the combination math — that would reinvent error compounding through the back door. Instead, two conservative couplings:

  • Confidence caps: ≥2 unverified load-bearing assumptions on the record → confidence capped at "low"; exactly 1 → capped at "medium". Raw counts always stored.
  • Fragility pull (the docs/03 graft, node-level): a node resting on ≥1 unverified load-bearing assumption has its estimate pulled toward its outside-view base rate by fragility_pull_weight (default 0.15 in log-odds space). Weight 0.0 disables it, and the pull is recomputable from stored raw values — so experiment 003 can score v2 with and without it from the same records, free.
Review prompts
  • Is 0.15 a sane default strength for the pull? (0 = off, higher = more skeptical of fragile nodes.)
  • Do the confidence caps (2→low, 1→medium) match your intuition?

decisionPer-leaf retrieval top-up

The v1 deferral comes due — leaves can get their own targeted search.

An evidence leaf poorly covered by the shared bundle (no bundle source mentions its key terms) gets ONE targeted search appended to its context. Shares the per-question budget with assumption verification; verification has priority (leaf_topup_max_searches, default 2). This was your P0 "revise" on v1's shared-bundle-only design, now unlocked because assumption-checking needs the targeted search machinery anyway.

contextBadges & the postmortem view

What you'll actually see in the rendered argument.

render-forecast shows every node's assumptions as verified ✓ falsified ✗ unverified ○ badges with their one-line evidence. When a forecast eventually misses, "which assumption broke?" becomes a mechanical lookup — the postmortem hook you asked for on day one, now structural.

contextCost & config

What v2 adds to the bill and what you can tune.

v1 (~$0.20/q) + up to 6 verdict calls (cheap model, ~$0.01 each) + ≤8 extra search credits/question ≈ $0.25–0.45/question — still under the ensemble.

New knobs, all in settings.toml [pyramid]: max_assumption_verifications, leaf_topup_max_searches, fragility_pull_weight, the two confidence-cap counts, plus [tasks.assumption_verdict] (its own model config).

planEvidence plan & non-goals

How v2 earns its way in, and what it deliberately excludes.

Experiment 003: v2 vs v1, paired, same bundles — registered only after 002 is underway. Primary: paired Brier delta. Secondaries: verified-false catch rate (how often verification repairs a node — the direct measure of your idea's value), fragility-pull on/off recomputation, cost delta. v1's shipped defaults change nothing until 003 reports.

Not in v2: cross-question assumption graphs (a shared world model); recursively decomposing assumptions; assumptions as multiplied conjuncts; multi-round verification loops.
